# 演習: 同じ検査をCIで繰り返す

自分のPRの最新コミットに対するSAST・テストの結果を確認します。検査の成功はアプリ全体の安全性を保証しません。

## 1. 開始状態を確認する

自分の作業ブランチで実行します。

```sh
git branch --show-current
python -m pytest -q
semgrep scan --config r/python.flask.security.injection.tainted-sql-string.tainted-sql-string --error app/
```

修正後の期待結果はテスト73件成功・SQLインジェクションの指摘0件です。ここでは`r/`で指定した既存ルール1つを使い、`--error`で指摘がある場合に終了コード1を返します。失敗が残れば内容を記録します。テストや検査を弱めて成功にしないでください。

## 2. CIの雛形を追加する

```sh
python scripts/enable_ci.py
```

`.github/workflows/checks.yml`を開きます。既存ファイルがある場合は上書きせず、講師と確認してください。

| 設定 | 役割 |
|---|---|
| on | PRの更新、main・lesson・末尾が/lessonのブランチへのpushで起動 |
| permissions | リポジトリの読み取り権限 |
| matrix.check | pytestとsemgrepを別のジョブで実行 |
| run | テスト、全体検査の結果表示、SQLインジェクションの合否判定 |

Python 3.12と固定した依存一覧を使います。OSやPythonのパッチ版まで同一という意味ではありません。Registryのルールは更新で内容が変わる可能性があります。

Semgrepジョブは、まず`p/owasp-top-ten`の全指摘をログに残し、次にSQLインジェクションの既存ルールで合否を判定します。全体検査には`--error`を付けず、SQLインジェクションの検査には付けます。通信・解析等の問題は別扱いで、`--strict`も使って確認します。CIはこのDockerfileを使わないため、`--metrics=off`も明示しています。

**この演習のCI成功は、SQLインジェクションの修正と既存テストの成功を表します。** 選択課題の2件は残っていても成功します。未対応の指摘はIssueで管理し、[選択課題](08-extra-findings.md)で修正した後に全体検査も必須にします。

手元と同じ`.semgrepignore`を使い、Jinjaテンプレートは検査対象外です。指摘を消すために除外対象を増やさず、検査の範囲をPRにも記録してください。

## 3. 変更を送信する

```sh
git add .github/workflows/checks.yml
git diff --cached
git commit -m "Add CI checks for the lesson"
git push
git rev-parse HEAD
```

自分のPRから最新の変更のチェック結果を開きます。pushとPRで2回実行される場合があります。以前の成功を今回の結果と取り違えないでください。

## 4. 結果を読む

- 自分のPRの最新コミットに対する実行か確認する。
- pytestとsemgrepの両ジョブが実行されたか確認する。
- テストの結果と、Semgrepの検査対象・指摘・エラーの有無をログで確認する。
- ジョブ全体が待機中・実行中・キャンセル・スキップ・未実行の状態を成功扱いしない。

この教材は、同じ雛形からpytest用とsemgrep用の2ジョブを動かします。pytestジョブ内のSemgrep用ステップと、semgrepジョブ内のpytest用ステップがスキップされるのは意図した動作です。それぞれの担当の検査ステップが実行され、結果が記録されていることを確認してください。

修正後は両ジョブの成功を期待します。失敗した場合は、問題の検出なのか、依存取得や通信で検査自体が動かなかったのかを区別します。

PRに対象コミット、実行へのリンク、結果、未確認事項、採用の根拠または追加対応を書きます。全員のマージは必須にしません。

## 5. 脆弱な変更を検出できるか確かめる

両ジョブの成功を確認してから進めます。作業ツリーに未保存・未コミットの変更があれば先に保存し、講師と確認してください。この演習では、まだmainへマージしません。

まず修正済みのコミットを記録します。同じターミナルを使います。

```sh
git status --short
lesson_fixed_commit=$(git rev-parse HEAD)
git show "$lesson_fixed_commit" --oneline --no-patch
git show main:app/main.py
```

表示された修正済みSHAもメモし、復元まで同じターミナルを使います。mainに初期版のSQL文字列への入力埋め込みが残っていることを確認します。既にmainを修正した場合は、この手順を続けず講師に相談してください。

SARIFは`.gitignore`の`semgrep-*.sarif`で除外されます。`git status --short`にSARIFが出る場合は教材の更新状況を講師と確認し、無理にcommitして進めないでください。

```sh
git restore --source=main -- app/main.py
git diff -- app/main.py
git add app/main.py
git commit -m "Demonstrate CI catching vulnerable search"
git push
```

このコミットに対してpytestとSemgrepが失敗することを、PRのログで確認します。通信エラーなどによる失敗とは区別してください。ポートは引き続きPrivateです。

## 6. 修正済みの状態へ戻す

上で記録したコミットから、検索ファイルだけを復元します。変数を失った場合はGitの履歴から修正済みのコミットを確認し、講師と復元元を確かめてください。

```sh
git status --short
git show "$lesson_fixed_commit" --oneline --no-patch
git restore --source="$lesson_fixed_commit" -- app/main.py
git diff -- app/main.py
git add app/main.py
git commit -m "Restore parameterized search after CI exercise"
git push
```

PRの最新コミットで両ジョブが再び成功することを確認します。成功→脆弱な変更で失敗→修正を戻して成功、の3つのコミットと結果を記録してください。**失敗を表示することとマージを禁止することは別**です。マージ禁止には必須チェックの設定が必要です。

## CIが利用できない・実行待ちの場合

11:31を目安に講師の実行例でログを読みます。自分のCIは未完了として記録し、講師の結果を自分の結果と扱わないでください。後で自分のPRの実行結果を確認します。

| 状況 | 確認すること |
|---|---|
| ワークフローが出ない | ファイルのcommit・push、PRと対象ブランチ |
| Actionsが無効・利用枠の問題 | 自分のリポジトリの設定と利用条件。無断で課金設定を変更しない |
| 検査の失敗が残る | 同じ検査のローカル実行とpush漏れ |
| 通信・導入エラー | 該当ステップのログ。検査による問題の検出と区別する |

## 補足: 取り込み条件とActionの固定

CIの実行と、成功をマージ条件にする設定は別です。GitHub FreeのPrivateリポジトリではブランチ保護を利用できないため、今回はCIの結果を自分で確認します。必須チェックやレビューをマージ条件にする仕組みはスライドで紹介します。リポジトリをPublicに変更する必要はありません。

雛形のActionはタグ参照です。SHA固定は補足とし、必須演習の終了条件には含めません。試す場合は次を実行して差分を確認します。

```sh
python scripts/install_pinact.py
.tools/pinact run .github/workflows/checks.yml
git diff -- .github/workflows/checks.yml
.tools/pinact run --fix=false --no-api .github/workflows/checks.yml
```

固定は安全性の保証ではありません。参照先の確認と継続的な更新が必要です。組織がSHA固定を必須にしている場合は設定を緩めず、講師と固定済みの設定を用意します。

講義の最後に講師の案内で、[作業の保存・環境停止](99-finish.md)を行います。
